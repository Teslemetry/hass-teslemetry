# Agent instructions

This repository is the **HACS beta release** of the Teslemetry integration for Home Assistant. The only code that matters is in `homeassistant/components/teslemetry/`. Everything else is upstream HA core scaffolding for testing.

## Task: build a release

```bash
./release.sh <major|minor|patch> [--line <major.minor>]            # dry run, stops before publish
./release.sh <major|minor|patch> [--line <major.minor>] --publish  # arms the real tag + GitHub release
./release.sh daily [--waive <#N|fork#N>]... [--exclude <#N|fork#N>]... [--approve-requirements <digest>] [--publish]
                                                                   # headless daily pre-release v<UTC Y.M.D>, plus a soaked latest when its rules pass
                                                                   # either mode also takes --lower-floor <version>; see hacs_floor_gate
```

`release.sh` (repo root) **is** the release process and owns the HOW — read its header comment for the step list. This file owns the WHY and the gotchas. Do not re-add hand-run step lists here; they drift from the script.

`release.sh` is a **fork-only tracked file at the repo root**, like `.github/workflows/teslemetry-test.yml` and `release.yml`. Core `dev` has no `release.sh` and the CI-strip only touches `.github/workflows/`, so the core-`dev` sync never clobbers it. Do not move it under `script/` — that tree is core-synced and the name could collide upstream.

The pipeline runs every phase automatically and fail-stop. It **never** runs `git checkout main`; it rebases only its temporary `sync-dev` branch and pushes `main` with `--force-with-lease` on the `main` it fetched, so it is safe from an isolated worktree. It hands control to you at exactly three points (in `daily` mode each one is a headless stop instead: the run prints why and exits 3 with nothing published):

- **Any conflict rerere cannot replay** — except a modify/delete on a `CORE_CI_PATHS` workflow, which the rebase resolves itself by keeping it deleted and logging `kept deleted:` — a conflict rebasing `main`'s commits onto the core base (see "The pinned core base"), or a PR net diff that doesn't apply cleanly. With `RELEASE_RERERE_CACHE` set to a persistent directory, `git rerere` replays every resolution recorded there by an earlier cut, and only a conflict it has not seen stops; unset, every conflict stops. Edit files directly (no `git mergetool`) and `git add` each resolved file **without committing or continuing the rebase**; the script finishes the commit or rebase and re-runs the conflict-marker grep.
- **The TEMPORARY `quality_scale.yaml` checkpoint** — the script excludes `quality_scale.yaml` from every per-PR diff (it conflicts repeatedly while quality-scale work is in flight) and, when an applied PR changed it, pauses once for you to write the correct combined final state and `git add` it. Retire the checkpoint and the exclusion together once the quality scale PRs have merged.
- **The approval pause** — reached only after the build gate passed in full. Type `publish`; anything else aborts with nothing published. `daily` mode has no approval pause; see "Publish safety".

### What a cut composes

A release is the pinned core base (below) plus, in `apply_prs`, one commit per PR in this order, each the PR's net diff (merge-base to head) applied with a three-way merge:

1. Every open Bre77 PR on `home-assistant/core` labelled `integration: teslemetry`, ascending by number. Commit subject `#<N>: <title>`.
2. Every open PR on the staging fork `Teslemetry/home-assistant` whose base is `dev` and that touches `homeassistant/components/teslemetry/` or `tests/components/teslemetry/`, draft or ready, ascending by number. Commit subject `fork#<N>: <title>`. These are staged changes still awaiting the captain's review, so their release-notes lines are marked `(staged, draft)` or `(staged, ready)`.
   With `PROMOTE_QUEUE` set to the ha-promoter queue file, only the fork PRs queued there are taken; a queued PR outside that open set is skipped with a note (ha-promoter closes a fork PR when it opens it upstream, and the change returns through list 1). A malformed or unreadable queue stops the cut. Unset, every matching fork PR is taken.
   A queue entry may end in `needs=core#<N>` or `needs=fork#<N>`: an approved PR built on an unmerged base ships in HACS before the base merges upstream. The cut takes it only with its base (composed in the same cut, or `core#<N>` merged into dev), applies it after the base, and diffs it from its merge-base with the base's head, because re-applying the base's change makes an add/add conflict on every file the base creates.

Both lists use `gh pr list --limit 200` (`PR_LIST_LIMIT`) and the cut dies if a list fills the limit. gh's default of 30 truncates silently, which drops the oldest PRs from a cut. To see today's compose set without cutting, `source ./release.sh` and run `list_core_prs` / `list_fork_prs`. Sourcing the script does not start a cut.

After both lists, `apply_fixups` commits each tracked patch in `release-fixups/` whose PRs the cut applied. A file name such as `core-174090+core-186075.patch` names the PRs (`core-<N>`, `fork-<N>`). A fixup reconciles two PRs that apply cleanly together but clash in meaning, such as a call to a signature the other PR changes. If any named PR is not in the cut, the fixup does nothing. If the patch no longer applies, the cut stops. Delete the fixup once either PR merges upstream.

`core-185983.patch` instead adapts one merged PR to the pinned core base. A latest fix build applies #185983's net diff on latest's own base, so its `test_climate.py` gets none of `main`'s climate shims; the patch rewrites its `ClimateEntityStateAttribute.TEMPERATURE_UNIT` keys and `native_*` temperature reads to `main`'s form. Delete it once the pinned core base has `ClimateEntityStateAttribute.TEMPERATURE_UNIT`.

### How the release line is selected

Versions bump off the latest release **tag** (`git tag -l 'v*'`, version-sorted). Tags are the durable record even when a release object is deleted (a yanked build whose tag is kept), and are the same source `aiopowerwall_pin_gate` reads.

A bare `sort -V | tail -1` lets a newer preview or minor line hijack an older maintenance line: with a `v6.1.x` tag present, a `6.0.x` maintenance `patch` cut would silently compute a 6.1 number. The line cannot be inferred from the branch being cut — release tags live on `release-*` branches never merged back (so `git tag --merged` finds nothing), `main`'s `custom_components/.../manifest.json` carries no version, and 30-plus historical `major.minor` series rule out "refuse when more than one series exists". So the line is stated explicitly:

- **`--line <major.minor>`** filters candidate tags to that series before taking the `sort -V` max. It names the series you compute **from**: `--line 6.1 patch` advances the 6.1 line; `--line 6.1 minor` births 6.2.0 off it; `--line 6.0 patch` continues 6.0 maintenance.
- **`require_unambiguous_line`** derives ambiguity purely from the tag list — no memory, no clock — and `die`s demanding `--line` when the newest tag is a pre-release (a preview line is open) or more than one minor line exists under the newest tag's major. It and the bump-off-newest lookup ignore the daily `v<UTC Y.M.D>` tags, whose four-digit-year major would sort above every 6.x tag. **6.0.x, 6.1.x and 6.2.x are all tagged, so this fires on every bump cut today: `--line` is effectively mandatory.**

The guard is deliberately not full inference — a *cross-major* stable transition (a stable `v7.0.0` while `6.x` is maintained) is undecidable from tags alone, and is caught by the pre-release condition while that line is still in preview. Do not "simplify" the guard back to a bare `sort -V | tail -1`, and do not weaken the parse/bump arithmetic it feeds: the point is that a forgotten flag stops the release loudly instead of shipping the wrong series.

### The pinned core base

A build's core is the core release tag that `hacs.json`'s `homeassistant` floor names (a full version such as `2026.10.0`), never core `dev`: the floor is the release the build claims to support, so the integration is tested against it. `hacs.json` is the only place the pin lives. Only `homeassistant/components/teslemetry/` and `tests/components/teslemetry/` come from `upstream/dev`. `sync_dev` builds a base commit (parent: the tag; subject `HACS core base: core <tag> with teslemetry from dev <sha>`) and rebases `main`'s fork commits, the ones after `main`'s previous base commit, onto it. `restore_core_base` puts every core-owned path outside the integration at the tag, except `homeassistant/generated` (data made from the manifests, such as teslemetry's Labs preview features in `labs.py`, which a built-in integration needs and a HACS install reads from its own manifest), with the integration's own pins in `requirements_all.txt`. **TEMPORARY:** dev's teslemetry tests import their helpers from `pytest_homeassistant` (`packages/pytest-home-assistant`), which the pinned tag predates, so `restore_core_base` also writes an untracked `pytest_homeassistant` package at the repo root that aliases each `pytest_homeassistant.<name>` to `tests.<name>` (`alias_pytest_homeassistant`). It writes nothing on a tag that has the package; delete it once the pinned core base has `packages/pytest-home-assistant`. The build gate and `teslemetry-test.yml` run it first, so a core change a PR carries outside the integration never reaches the tests. `core_base_gate` stops a build that is not on its floor tag, and a latest is built only on a pre-release `main` that is.

If the integration (from dev, a core PR or a fork PR) needs core API newer than the pinned release, bridge the gap inside the integration with the API the release has. Never backport core code. The build gate fails until the gap is bridged.

Monthly pin bump, after core `X.Y.0` ships:

1. Open a PR to `main` that sets `hacs.json` `homeassistant` to `X.Y.0`. Its `teslemetry-test.yml` run tests the integration against the new tag.
2. Fix each failure inside the integration. Retire each compat shim below whose retirement condition the new floor meets.
3. After the merge, the next cut rebases `main` onto the new tag. A floor change holds latest for `--approve-requirements` (see `release.sh`'s header).

A cut based on a release **tag** inherits that tag's frozen copy of `release.sh`, which may predate current gates and flags. Any tag-based cut MUST adopt `main`'s current `release.sh` before resolving the version or running gates.

### What the gates guarantee (all fail-stop, enforced by the script)

- **Conflict-marker grep after every commit** over the integration + tests.
- **`core_base_gate`** — the composed build sits on the core tag its `hacs.json` floor names; see "The pinned core base".
- **`subentry_migration_gate`** — `hacs_migrate_subentry_entities` defined, called, and its tests present in the composed build.
- **`aiopowerwall_pin_gate`** — the composed pin never drops below the last shipped tag's.
- **`subentry_translations_gate`** — every `SUBENTRY_TYPE_*` value in the composed `const.py` has a non-empty `config_subentries.<type>.initiate_flow.user` (the string the `+` button renders) in both `strings.json` and the separately-compiled `translations/en.json`. Nothing else tests this, so a `strings.json` conflict resolved by keeping one side ships a bare unlabelled button and an unlabelled setup flow with a green build. The block is not HACS-only — a correct cut restores it and this gate proves it did. Never hand-edit `translations/en.json` to satisfy it; fix `strings.json` and recompile. Retire once every declared subentry type's translations land and stay on `main` with no per-cut compose step.
- **`core_constraints_gate`** — the composed `manifest.json` `requirements` resolve (`uv pip compile`, nothing installed) under the `homeassistant/package_constraints.txt` of the core releases the build claims to support, read from the composed `hacs.json` `homeassistant` floor: the floor release itself (the core tag equal to the floor) and the newest released core at or above it, pre-releases counted only while no stable release at or above the floor exists, each at its own Python requirement. Core installs requirements under those constraints and the build gate does not apply them, so a pin that conflicts with them ships green and then cannot install. Nothing else tests this. `NOT INSTALLABLE` is the resolver's verdict; `UNVERIFIED` means no verdict was reached — a network or tooling failure, or a floor whose core tag does not exist yet — and never falls back to stable or dev. Both stop the cut. The floor is a claim the gate holds the build to: when the pins cannot install on the floor release, fix the pins or raise the floor to a release they do install on. Write the floor as a full core version (`2026.10.0b0`, not `2026.10`). `CORE_CONSTRAINTS_PREVIEW_REF=<core ref>` prints an extra preview resolution that never affects the verdict and is refused with `--publish`. To check without cutting, `source ./release.sh` and run `core_constraints_gate [manifest.json] [hacs.json]`.
- **`subentry_migration_gate`** also checks that `hacs_remove_empty_holder_subentries` is defined and called after `hacs_migrate_subentry_entities` in `async_setup_entry`.
- **`beta_migration_gate`** — `beta_migration_fix` defined and called from `async_setup_entry`.
- **`logship_gate`** — `async_setup_entry` still gets, acquires and releases the log shipper and calls `_async_setup_option_reload`, `logship.py` exists, and `config_flow.py` keeps its options flow with the `ship_logs_to_clickstack` choice.
- **`issue_tracker_gate`** — `manifest.json` `issue_tracker` is `https://github.com/Teslemetry/hass-teslemetry/issues`.
- **`hacs_floor_gate`** — the composed `hacs.json` floor is not below the last shipped tag's (a latest build compares with the current latest). A floor below it ships green and HACS offers the build to cores it was never tested on. To lower the floor on purpose, pass `--lower-floor <the composed floor>`; a value that does not equal the composed floor does not pass.
- **`latest_superset_gate`** — a new latest keeps every change the current latest shipped: in the compose (a promoted fork PR counts as its core PR), merged into its base, kept out by an open blocks-latest issue, or named by `--exclude <#N|fork#N>`, the captain's acceptance of that one drop. Anything else stops the run with nothing published, so a planner or compose bug cannot silently drop a shipped fix. It logs one `latest change set vs <tag>: added ...; removed ... (reason); kept ...` line before publishing.
- **Full build gate** against the pinned core base, mirroring `.github/workflows/teslemetry-test.yml` command-for-command. This is the real publish gate for this repo; there is no branch-protection required-check.

### Publish safety

Two independent gates guard a bump cut's real release: the interactive `publish` confirmation **and** the `--publish` flag. Without `--publish`, even an approved run stops at a dry run, so validating the pipeline never risks a real tag or release. With both, the script tags `v$VERSION`, zips the integration, runs `gh release create ... --prerelease` + upload, then **guarantees** the prerelease flag with a typed API PATCH (`gh api --method PATCH .../releases/$id -F prerelease=true`; never `gh release edit`, which resets it), and pushes `release-$VERSION`. A `daily --publish` run takes the same publish steps, titled `Pre-release v…`, once every gate passes, with no confirmation, and pushes the dev sync to `main` only then; if `main` moved during the run it stops with nothing published. When the run also builds latest (rules in `release.sh`'s header), it tags latest before the pre-release, publishes the pre-release first, and creates latest last with `gh release create ... --latest` and no `--prerelease`. A `daily` run without `--publish` pushes nothing, `main` included.

## Conflict resolution guidelines

- Preserve the intent of both the upstream change and the PR change; read the full PR diff first.
- Follow HA coding conventions: f-strings, type hints, Python 3.13+, American English, sentence case. Keep try blocks minimal; process data after the try/catch. Lazy logging (`_LOGGER.debug("Message with %s", variable)` — no periods, no integration name). Entity names use `_attr_translation_key`, never hardcoded strings. Ruff owns formatting.

PRs are based on different upstream commits, so a later PR may revert an earlier one. Watch for:
- A PR re-introducing old code a previously-applied PR already changed (e.g. reverting translated exceptions back to plain strings).
- Two PRs both creating the same new file — combine them into one file with a shared `async_setup_entry`.
- Nested conflict markers (`<<<<<<< ours` inside another) from three-way merge fallback — always grep after committing.

## HACS-only patches

These live only in this HACS tree, never upstream, and must survive PR application and conflict resolution. Some ride `main`, including the TEMPORARY compat shims: the sync replays them on top of dev's integration and conflicts wherever dev changes their lines, so keep the fork's form.

Land every fix on `main`, never only on a `release-*` branch, and cut again: release branches are never merged back, so a fix made only there is lost from the next cut.

- **`beta_migration_fix`** (`__init__.py`) — backfills `auth_implementation` for early beta installs. No dev test sets up such an entry, so a dropped call ships green; `beta_migration_gate` catches it.
- **Opt-in ClickStack log shipping** — the `logship` acquire/release block in `async_setup_entry` plus `logship.py`. Shipping has a single durable authorization gate: the per-entry config option `ship_logs_to_clickstack` (options flow in `config_flow.py`, default off), tracked as a force-count on the per-`hass` `TeslemetryLogShipper` singleton, with `is_shipping_authorized()` the single source of truth. It is deliberately *not* tied to the live DEBUG log level — that coupling silently drops shipping on restart whenever the user's debug-logging choice isn't "persistent". A change to the option reloads the entry (`_async_setup_option_reload` reloads only on that option, not on every entry update) so the force-count re-derives. The shipper takes the integration's logger name from `LOGGER.name`, never a hardcoded `homeassistant.components.teslemetry`: a HACS install runs as `custom_components.teslemetry`, so a hardcoded name ships nothing. `logship_gate` checks the setup calls.
- **`hacs_migrate_subentry_entities`** (`__init__.py`) — standing cross-version registry normalization for any install that ever ran the entity-parenting subentry layout (v5.2.0, v5.3.0, v6.0.0, v6.0.1). Runs before any inventory or subentry cleanup and moves Teslemetry entities and devices onto the main entry without changing unique IDs or entity IDs, preserving every config-holder subentry and its local-control credentials. It is **release-branch-only unless merged back to `main`**: release branches that carry it and are never merged back leave the next cut starting from a `main` that lacks it, silently. `subentry_migration_gate` — not documentation — is what keeps it alive. Retire only with evidence that no such install can still upgrade directly, removing the function, its call, its tests, the gate, and this bullet together.
- **`hacs_remove_empty_holder_subentries`** (`__init__.py`) — removes the unpaired auto-created holder subentries older builds left behind. It MUST run after `hacs_migrate_subentry_entities` in `async_setup_entry`: run first, it removes holders that still own records. `subentry_migration_gate` checks the order. Retire with `hacs_migrate_subentry_entities`.
- **`aiopowerwall` downgrade guard** — core and `main` both carry the `aiopowerwall` pin now, so a cut needs no pin restore step. `aiopowerwall_pin_gate` stays as a cheap guard: an older PR that carries a lower pin would downgrade the library and break local grid import/export, and the build gate cannot see it (both versions import cleanly).
- **Boolean config entry returns** (`__init__.py`) — **TEMPORARY.** `async_setup_entry`, `async_unload_entry` and `async_migrate_entry` return `bool`, and unload calls `async_unload_platforms`, never `async_unload_platforms_or_raise`. The pinned 2026.10.0 base fails a setup that does not return a boolean and has no `async_unload_platforms_or_raise`. The sync re-introduces dev's form wherever dev changes these lines: keep the fork's form. The build gate catches a regression, because every setup test fails. Retire the shim and this bullet together once the floor reaches the first core release where `async_setup_entry` may return `None`.
- **`issue_tracker`** (`manifest.json`) — points HA's "report issue" link at this fork's tracker. Core's manifest has no such key, so a conflict resolution that takes core's side drops it; `issue_tracker_gate` catches it. See also `--skip-plugins manifest` under "CI".
- **Stable-core climate temperature attributes** (`climate.py`) — **TEMPORARY.** The climate entities set `_attr_temperature_unit`, `_attr_current_temperature` and `_attr_target_temperature`, never the `_attr_native_*` forms core dev uses (a compat comment mention is allowed). The pinned 2026.10.0 base has no `_attr_native_*` climate API, so the native form raises `AttributeError` while HA adds every Teslemetry climate entity, and they show unavailable. `snapshots/test_climate.ambr` carries no `temperature_unit` state attribute for the same reason. The sync re-introduces the native form wherever dev changes these lines: keep the fork's form. The build gate's climate tests catch a regression. Retire the shim, the snapshot change, and this bullet together once the floor reaches the first core release with `_attr_native_temperature_unit` on `ClimateEntity`.
- **Stable-core DeviceInfo key access** (`__init__.py`, `config_flow.py`) — **TEMPORARY.** `async_setup_energy_device` sets `energysite.device["model"]` and `["sw_version"]` by key and registers the device with `async_get_or_create(**energysite.device)`, never `async_get_or_create_device`, and `_energy_site_name` reads `energy_data.device.get("name")`, never the attribute form core dev uses (a compat comment mention is allowed). The pinned 2026.10.0 base's `DeviceInfo` is a `TypedDict` and its device registry has no `async_get_or_create_device`, so dev's form raises `AttributeError` and energy site setup fails. Dev's `DeviceInfo` class still accepts the key form. The sync re-introduces the attribute form wherever dev changes these lines: keep the fork's form. The build gate catches a regression, because every energy site setup test fails. Retire the shim and this bullet together once the floor reaches the first core release where `DeviceInfo` is a class and `async_get_or_create_device` exists.

## CI: the clean per-integration gate

`.github/workflows/teslemetry-test.yml` is the only PR/push CI gate this repo keeps: a fork-owned file running `pytest tests/components/teslemetry`, ruff, and integration-scoped hassfest against the pinned core base (its first step runs `restore_core_base`) on every PR/push to `main` and push to `release-*`. Treat it as the pass/fail signal for the integration's health.

Core `dev` carries a much larger `.github/workflows/` set that would run whole-repo and fail here as fork-irrelevant noise. It is deleted, and `release.sh`'s `strip_core_ci` re-deletes it every cut. Keep this list in sync with `CORE_CI_PATHS` in `release.sh`: `ci.yaml`, `validate.yml`, `check-requirements-deterministic.yml`, `check-requirements.lock.yml`, `check-requirements.md`, `codeql.yml`, `translations.yml`, `builder.yml`, `wheels.yml`, `e2e-tests.yml`, `quality-scale-reviewer-trigger.yml`, `quality-scale-reviewer.md`, `quality-scale-reviewer.lock.yml`, `matchers/`. A red check from any of these means the strip didn't run or missed a path — not a signal about the integration.

Kept alongside `teslemetry-test.yml` because they aren't PR/push CI noise: `release.yml` (posts the GitHub release to Discord) and the issue-automation bots `detect-duplicate-issues.yml`, `detect-non-english-issues.yml`, `stale.yml`, `lock.yml`, `restrict-task-creation.yml`.

- **`--skip-plugins manifest` is structural, not a workaround-of-convenience.** `manifest.json`'s `issue_tracker` key (this fork's own tracker) is deliberate, but hassfest's `manifest` plugin only permits it on integrations it treats as "custom", and it classifies anything under `homeassistant/components/` as core regardless of `--integration-path`. Skipping that one plugin avoids a permanent false positive; everything else hassfest checks still runs.
- **Test dependencies**: `requirements_all.txt` + `requirements_test.txt` (+ `requirements_test_pre_commit.txt` for ruff). There is no `requirements_test_all.txt` in this checkout — don't chase it if you see it referenced.
- **Compile translations for ALL integrations before `pytest`** (`python3 -m script.translations develop --all`, <1s, no network) or `check_translations` (`tests/components/conftest.py`) fails any test touching a platform teslemetry's entities inherit services from (e.g. `media_player`, `button`). `homeassistant/components/*/translations` is gitignored except teslemetry's own, so it is never pre-populated on a fresh checkout; a worktree with stale generated files from an earlier `--all` run falsely passes with only `--integration teslemetry` compiled — verify translation-dependent changes against a clean checkout.
- **This workflow cannot gate publishing** — `gh release create` is a manual command outside any workflow and this repo uses no branch-protection required-checks. The actual gate is `release.sh`'s `build_gate`, which runs the same suite locally before the approval pause.
